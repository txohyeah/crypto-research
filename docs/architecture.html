两个接缝Seams — 变化被隔离的地方

接缝① Evaluator → Digest

agent 会话 / 未来 API 调用  --JSON文件--> deliver_digest --stdin/--digest--> validate()
  • 载体是 /tmp/web3_digest.json 文件，不传内存对象 → 评估环节崩溃可单独重跑
  • date 必填字符串；major[] 每项 title 必填；opps[] 每项 what 必填
  • 缺 major/opps 键 → 容错空栏；title 缺失 → exit 2 拒绝渲染（fail-closed）
  • 校验函数与模板同文件（render_digest.py）——schema 的定义者和消费者永不脱节
  • 换 Evaluator 实现（agent → API）时此契约零改动

接缝② render / deliver 分离

digest JSON --> render(d) : str  ·  html_path --> send_file(path)
  • 渲染是纯函数 dict→str；投递是纯函数 path→file_key
  • 两者之间唯一的耦合点是 out/YYYYMMDD区块链早报.html 一个文件
  • 新增渠道（RSS/邮件/Telegram）= 新写一个 Channel 文件 + deliver 加一行分支
  • dry-run 模式停在第④步：全链路可测而不打扰用户
  • 行情/健康快照在渲染前注入，模板永远不知道数据从哪来

压缩阶梯位置Compression Ladder — 决策权放在哪

判据只有一个：LLM 还剩多少自由裁量权。下沉方向：Prompt(1) → Skill(2) → Tool(3) → Plugin(4)。 第 4 层不是"更好的工具"，是把"什么时候做、做的对不对"从模型手里拿走。

collect.py cron 触发自动执行，无选择点：直连→代理→记故障，路径唯一 第4层 Plugin
digest_raw.py 确定性 CLI，参数固定输出确定；但由上游决定何时调它 第3层 Tool
Evaluator ⚠️ 每次 cron 唤醒全新会话现场判断——规则未沉淀前故意留在低层，硬编码未稳定的规则等于把浆糊浇筑成混凝土 第1-2层 P1后 → L3
deliver_digest.py 幂等/校验/落账全是 if 和 SQL；fail-closed + delivered 单调守卫 + 只增审计 第4层 Plugin
send_feishu_file.py 纯 Channel 函数，无任何模型参与；渠道整体可替换 第4层 Plugin
下沉判据：规则稳定 + 可枚举 + 执行路径唯一 → 压到第 4 层；需要语义理解、存在例外 → 留在上面。 本项目的演进路线 = 逐环节爬梯：已爬顶的环节（采集/渲染/投递/记账）永远不再需要模型； Evaluator 等 P1 规则沉淀完成（Phase B）升到第 3 层，届时整条链退化为纯代码 + 一次裸 API 调用， cron 从 agent 型降级为 shell 型——借 DeepSeek Harness 的判据与纪律，不搬它的微内核形态。

三条不可妥协的设计约束Invariants

Evaluator 无状态、禁碰网络 只吃给定条目。幻觉控制靠架构隔离——它物理上够不到编造信息的途径，而不是 prompt 里求它别编。
run_id = 日期做幂等 同日已 delivered 的 Run 重跑直接跳过；采集重跑不得降级其状态。cron 重试、手动补跑都安全。
render 与 deliver 分离 内容决策与触达渠道互不知晓。换渠道零改动内容，换渲染风格零改动投递。
